# 数据结构与后端接入分析

本文件记录当前本地数据的语义和未来接入后端时的兼容约束。本地发送统计、旧统计分片升级、收藏导入预览与恢复、设置字段合并已实现；后端、账号和跨设备业务数据同步仍仅为建议。

## 当前持久数据

| 数据 | 存放处 / 标识 | 当前结构与用途 | 兼容注意 |
| --- | --- | --- | --- |
| 扩展设置 | `chrome.storage.sync` | `ExtensionSettings`：总开关、四平台开关与颜色、胶囊、操作、雷达等；语言偏好另存 | `mergeSettings` 补默认值；设置页与雷达开关通过后台串行提交叶子字段补丁，读取最新原始对象合并，保留未知字段。 |
| 收藏 | `chrome.storage.local` / `danmakuEchoFavoritesV1` | 数据库 `schemaVersion: 2`、`revision`、`writeId`、`items`；单条含正文、富内容 parts/assets、来源房间、标签、排序和发送计数 | key 名仍为 V1，**不能用 key 后缀判断内部 schema**；仓库可读取旧字段并规范化。主数据损坏时尝试 `danmakuEchoFavoritesBackupV2`，导入前另存 `danmakuEchoFavoritesBeforeImportV2`。 |
| 运行日志 | `chrome.storage.local` / `danmakuEchoRuntimeLogsV1` | `schemaVersion: 1`，有界的警告、错误及脱敏发送失败证据 | 诊断数据，保留 7 天、最多 500 条/约 1 MB；默认不应同步到后端。 |
| 雷达首次说明 | `chrome.storage.local` / `danmakuEchoRepeatReminderOnboardingV1` | 本机确认标记 | 纯 UI 状态，不属于业务历史。 |
| 抖音表情目录 | `chrome.storage.local` / `danmakuEchoDouyinEmojiCatalogV1` | 有效期缓存，含目录版本和条目 | 可重新抓取，不应迁移为用户数据。 |
| 插件发送统计 | `chrome.storage.local` / `danmakuEchoSendStatisticsIndexV1` 与 `danmakuEchoSendStatisticsDayV1:YYYY-MM-DD`，另有 V2 事件与索引块 | 全局索引仍为 V1；日数据兼容 V1 数组和 V2 汇总。事件为 `{id, platform, roomId, sentAtSec, text?, confirmation?}` | 无索引视为空；有索引但缺日数据会报部分不可读。缺少 `text` 或 `confirmation` 保持原样；未知 schema 拒绝写入。旧数组在该日下一次追加时升级并备份。 |

雷达近 60 秒弹幕样本、提示队列、发送关联、观众/贵宾短期样本以及页面诊断缓冲仅在运行时内存。它们不是持久历史，也不适合回填到后端。

当前兼容保护与后端仍需处理的边界：

- 收藏读取和导入已拒绝未知的 `schemaVersion`，遇到未来主库不会用旧备份覆盖它。导入预览显示新增、变更、移除条数，并在后台检查预览时的 `revision`；导入前保存备份，设置页可恢复。升级前发布的旧扩展不具备这些新保护，仍不能保证任意降级写入安全。
- 收藏的 `createdAt` / `lastSentAt` 用毫秒，新增统计的 `sentAtSec` 用秒。后端字段名和校验必须带单位；不能仅按数值猜测。收藏的 `roomKey` 是 `${platform}:${roomId}`，新统计保留独立 `platform`、`roomId`，后端宜用复合字段而非字符串拆分。
- 设置补丁只更新实际编辑的叶子字段。不同本地页面的不同字段修改能够合并，同一字段按后台处理顺序生效；界面等待本批保存结束后刷新，保留保存失败的草稿。它不提供跨设备原子事务，也不能约束旧扩展直接覆盖对象。

## 新增统计的含义

统计从四平台插件发送流程共同使用的 `SendCoordinator.finish(..., true)` 产生，不统计原站手动发送、回复草稿、复制、仅点击按钮、平台拒绝或未确认的请求。一次发送尝试使用随机 `id` 去重，并在尝试开始时固定房间 ID，避免切房后误归属；秒级时间为**现有发送流程判定成功的本机 UTC Unix 秒**。今日和按日汇总明确使用 UTC，单条时间按浏览器本地时区显示。详情每页 50 条，可按 UTC 日期、平台、房间和正文筛选；筛选同时用于导出和清理，全历史总数不随筛选改变。页面每秒数量只包含当前页，完整每秒数量在导出中计算。

新记录的 `text` 只保存实际发送的文字、Unicode Emoji 和可用的表情文字名称（例如 `[微笑]`），图片发送只保存文字表示；不保存富内容 parts/assets、图片地址、资源标识、页面 HTML 或请求体。正文中本来就有的链接或尖括号仍按普通文本保留，界面不解析成 HTML。缺少文字表示时保存空字符串；旧记录缺少 `text` 字段时显示“旧记录未保存正文”，并保留其缺失状态，避免与无文本发送混淆。统计仅保存在本机，可导出与清空，诊断日志仍不保存正文。

“判定成功”沿用当前平台发送策略，不能一概解释为服务器已广播或观众已看到。新记录的 `confirmation=platform` 表示成功判定同时观察到非 pending、非 requestOnly 的业务成功码 `0`；其他成功记录标为 `page`。HTTP 200、仅观察到请求都不会提升为平台确认，失败或未确认的发送仍不计数。旧记录缺少级别，不反推补齐。后端若需要更严格的成功率，需要另行定义广播或接收确认。

### 统计存储和查询

- V2 日汇总保存总数和平台数量；`danmakuEchoSendStatisticsEventV2:<日期>:<id>` 单独保存事件，`danmakuEchoSendStatisticsChunkV2:<日期>:<块号>` 每块最多保存 128 个 ID。追加只读取当日摘要、去重键和末块 ID，避免反复复制当天全部正文。
- V1 日数组仍可直接读取，首次向该日追加时同时写入 V2 数据及 `danmakuEchoSendStatisticsBackupV1:<日期>` 原始备份；不会启动全历史迁移。升级到 V2 后不保证旧扩展可读取，可使用本版 JSON 导出保留可移植历史。批量 `storage.set` 不等于跨多次调用的事务。
- V2 汇总不读取事件正文；详情使用日期和块内位置游标，新追加不改变已翻页记录的位置。正文筛选、导出和局部清理仍需扫描候选事件，没有宣称全文索引或恒定查询耗时。
- 写入与清理由同一个后台实例串行处理。后台不可用时设置页仍可直接读取、导出，但不退回页面直接清理，以免覆盖并发发送。不可读分片会保留并提示，清理遇到损坏数据会失败。
- 写入失败尽力记录 `danmakuEchoSendStatisticsHealthV1`，设置页显示最近的保存异常；存储完全不可写时也可能无法保存该标记。保留原发送结果，客户端仅重试统计一次，不重发弹幕。没有自动删除历史的保留策略，需由用户导出、清理。

旧收藏的 `totalSendCount` / `roomStats.sendCount` 只覆盖收藏重发，并非全部插件发送；`lastSentAt` 只保留最后一次时间。因此**不能从旧收藏数据推导历史逐秒记录**，也不能把这些数字直接相加到新统计，否则会重复和误计。新统计从升级后的第一次成功发送开始；旧累计可作为标注为 `legacyFavoriteSendCount` 的独立参考值，不能伪装成完整发送总数。

## 兼容与后端建议（待实现）

1. **先固定语义再设计 API。** 建议分别定义 `send_attempt`、`client_confirmed_send`、`server_acknowledged_send`；当前事件来自客户端判定，并带可选的确认依据。事件包含 `eventId`（目前的尝试 ID）、`occurredAtSec`（UTC 秒）、`platform`、`roomId`、`schemaVersion`、`source=extension`，未来可附 `clientVersion`。正文和身份信息默认不上传。
2. **以事件 ID 幂等导入。** 后端对 `(installationId, eventId)` 建唯一约束；不要只按时间、平台和房间去重，同一秒可能合法发送多条。安装标识应在用户授权同步后单独创建并持久化，不能用浏览器指纹代替。服务端保留接收时间以识别本机时钟偏差。
3. **同步采用本地优先与游标确认。** 先读取本地分片，按批发送；服务端确认后推进单独的同步游标。离线、重复请求、Service Worker 重启都允许重试。不要把“已发送请求”当“已持久化”；不要在导入成功前删除本地记录。账号切换时不得把不同账号历史自动合并。
4. **按 schema 显式升级。** 后端 DTO 与本地结构分开，写迁移函数处理旧收藏缺失的 `payload`、`tags`、`roomStats` 等字段，保留富内容 parts/assets 顺序。遇到未来未知 `schemaVersion` 应停止写入并保留原始备份；不能将未知字段规范化后静默丢弃。迁移前后以条数、ID 集合、富内容签名和导出回读结果校验。
5. **明确各类数据的所有权。** 收藏需要冲突策略（`revision`/`writeId` 仅用于当前本机写入校验，不能直接作为跨设备全局版本）；设置按字段合并或用户选择；日志、雷达缓存和首次说明状态保持本地。发送统计是追加事件，天然更适合并集去重，而非最后写入获胜。
6. **存储容量需在后端阶段评估。** V2 已减少单次追加写放大并提供分页，但没有自动清理，事件和旧格式备份仍占用 `chrome.storage.local`。接入后端前，应基于实际事件量决定已同步事件归档或 IndexedDB 迁移，并在迁移完成且校验通过后才清理旧分片。本地统计是尽力记录，不能作为结算凭证。

建议迁移验收覆盖：无本地数据、旧版收藏缺字段、含图文表情收藏、主库损坏但备份可用、同秒多条发送、重复上传、跨日期边界、时钟偏移、离线重试、Service Worker 重启、账号切换及降级运行。

### 可恢复清理与分页版本（2026-10-11）

- 后台仍为唯一写入者。`danmakuEchoSendStatisticsCleanupV1` 保存随机操作 ID、rewrite/remove 阶段、待删键与各日保留 ID；键按命名空间和日期合并前缀，不复制弹幕正文。保存任务失败时不修改索引或正文。更新索引、统计结构 revision 和 remove 阶段后，每 128 个键删除并读回核验，最后移除任务。批量存储调用不是跨调用事务。
- worker 启动、下一次写入、再次清理或「继续清理」会先恢复未完成任务。新追加必须等恢复结束，重复删除仅针对已捕获的键，不能误删后来追加的数据。清理提交后不提供取消；失败保留恢复任务。
- 「清空」无筛选时枚举已知 V1/V2 命名空间，清除孤立事件、索引块和旧数组备份。收藏、日志、未知版本命名空间不受影响；已知键内部的未来 schema 也不会强行删除。`getKeys` 不可用时，仅显式清理和容量检查允许 `get(null)` 兼容枚举。
- `danmakuEchoSendStatisticsRevisionV1` 的 ID 在删除或重排时更新，追加保持不变。游标包含此 revision，旧无版本游标要求回到第一页，但旧统计数据仍可读取。读前、读后均检查 revision 与清理任务；任务存在显示「正在清理」，不误报为数据损坏。其他设置页清理后，本页清空游标并重新加载。
- 设置页按 128 个日期分批读取日汇总，并在本地存储变更后使缓存失效；每次翻页复用汇总，正文按既有 128 条块读取。查询和导出支持 AbortSignal 与实际扫描进度，取消不修改数据。UI 导出按日排序后生成 Blob 分段，保留原 JSON 字段、秒汇总顺序与旧字段缺失语义；兼容消息 API 的对象形式仍可用。
- 容量显示使用浏览器 `getBytesInUse`，同时展示统计占用和 local 总占用；占配额 80% 预警、95% 强化提示，无法读取显示「暂不可用」。不自动删除历史，也不增加权限。
- 30／90／180 天快捷清理忽略当前筛选，确认框显示实际 UTC 截止日期与全平台范围。删除严格早于「今天 UTC 零点减 N 天」的记录，保留该边界日期当天；确认框与底层以包含式 `to`（边界的前一天）表达删除范围。仍沿用持久化清理流程。

这些改动没有新增后端模型或强制全量迁移；未来同步设计仍需遵守前述语义与授权边界。
