# Danmaku Echo 性能优化计划

更新日期：2026-09-16。范围：四个平台的页面运行时、雷达、发送诊断、本地存储及扩展加载。

本文保留优化前的源码审查与实施计划，包含当时尚未提交的发送失败日志增强。**第 2～4 节的“当前”“证据”描述的是优化前基线，不能再作为优化后的实现说明。** 本轮已经实施的范围、实测对照、回归结果和未覆盖部分见 [性能优化结果](PERFORMANCE_RESULTS.md)。历史回归结果见 [入口重构回归记录](ENTRY_REFACTOR_REGRESSION.md)，不能作为当前版本的性能基线。

## 1. 优化目标与约束

目标是减少高弹幕流量下的主线程占用、交互延迟和临时对象分配，并确认切房、全屏、隐藏恢复及长时间运行后资源能回收。

- 保持普通文字、Unicode Emoji、图片表情及混排的发送身份和顺序。
- 保持单条悬停、胶囊连续可达、正确发送者关联，以及斗鱼原生交互。
- 雷达保持 60 秒计数窗口、3 秒跨来源镜像去重、自动档预热与迟滞、同来源真实重复计数；不能用漏计换取速度。
- 抖音保持 MAIN/isolated world 边界与安全 DOM 接管。异常时恢复官方 Canvas，不主动拦截 WebSocket、不替换官方 Worker。
- 不增加常驻全页短周期扫描、无界缓存、逐条持久日志或新的扩展权限。
- 性能改动不顺带重构所有平台、升级依赖、改写存储用途或放宽测试断言。

## 3. 基线采集方案（P0）

### 3.1 对照方法

1. 固定机器、电源模式、浏览器版本、视口、缩放、视频清晰度和测试数据种子。记录 OS、CPU、内存、扩展版本、Git revision、未提交差异及构建时间；有差异时仅记录 commit 不足以定位产物。
2. 使用相同的脱敏 fixture，比较扩展关闭、扩展开启但雷达关闭、雷达开启三组；发送失败附件单独测量。四个平台分别记录，不能把 B 站结果外推到抖音。
3. 建议预热 30 秒、采样 120 秒，基线和改动后各执行 3 次，交替顺序。冷启动单独记录。报告每次结果与中位数，不选择最快一次。
4. 普通测量关闭 coverage；只在定位成本时开启详细 trace，并单独说明采集开销。保持前后台状态一致，不将隐藏标签页调度结果混入前台延迟。
5. fixture 保持输入确定性；真实直播间仅做补充验收，注明流量和站点状态变化，不能当作严格 A/B 对照。性能压测不向真实平台批量发送弹幕。

### 3.2 指标与门槛

| 指标 | 记录方式 | 验收口径 |
| --- | --- | --- |
| B 站悬停 | 现有 `bilibili-hover-performance` 场景 | 既有硬门槛：1,500 条侧聊、100 次悬停；有效样本至少 95；同步处理 P95 ≤ 16ms、胶囊可见 P95 ≤ 50ms、可见耗时最大值 ≤ 150ms |
| 主线程成本 | 浏览器 Performance trace，区分扩展脚本、站点脚本和布局调用栈；记录每秒 scripting 时间及长任务 | 新增测量项；不得把整页 CPU/掉帧全部归因于扩展。重点定位与扩展调用栈有关的 ≥ 50ms 任务 |
| 雷达处理 | 分开统计采集批次、单条 detector 输入、相似度计算及 UI 更新的 P50/P95/max | 建议初始目标：采集单批 P95 ≤ 4ms；需由目标设备基线校准，当前没有自动门禁 |
| 抖音帧处理 | 对 `advanceModelFrame`、`readFrame`、`commitFrame` 分段采样，记录活动轨道/节点数和刷新率 | 建议初始目标：扩展帧工作 P95 ≤ 4ms；这只是扩展份额，不能把整帧 16.7ms 全部分配给扩展 |
| 内存/资源 | 同一时机的 heap snapshot、detached DOM、实例/Observer/Timer/Map 计数；切房前后对比 | 静置超过对应 TTL、完成可比的 GC 后观察平台期；资源数不得随已销毁房间数持续增长。暂不设未经测量的固定 MB 门槛 |
| 失败日志 | 捕获/脱敏/发送消息/后台排队/存储分别计时；记录附件大小、写入次数及导出耗时 | 成功发送零 DOM 快照；原有容量和频率限制保持；失败诊断不能阻断下一次受保护交互 |
| 加载成本 | 各构建入口未压缩大小、实际注入次数、解析执行时间、首次 UI 可用时间 | 先建立平台及 frame 级基线；包体缩小本身不能证明运行更快 |

建议对候选优化设定推进标准：主指标在相同负载下有可重复改善，且超过基线波动；可先以 ≥ 15% 为候选收益目标，同时其它关键延迟不恶化超过 10%。这些百分比是**计划值**，不是已实现收益或现有 CI 门槛；基线不稳定时先解决测量问题。

保留未过滤和有效样本两套统计。现有 B 站 fixture 会识别调度暂停；必须同时报告暂停数量与有效样本数量，不能通过扩大过滤范围隐藏卡顿。

## 4. 原始优化项与验收要求

优先级表示排查和实施顺序，并非缺陷严重度。下面确认的是代码路径，性能瓶颈及收益仍需 trace/基准验证。

| 编号 | 优先级 | 范围 | 建议顺序及预期作用 | 风险 |
| --- | --- | --- | --- | --- |
| PERF-01 | P1 | 雷达检测器 | 增量维护计数与到期数据，减少每条输入的历史重扫 | 高：窗口、发送者计数和触发语义 |
| PERF-02 | P1 | 相似簇 | 缓存文本特征，减少同一候选的重复评分 | 中：数字、否定词、Emoji 等保护规则 |
| PERF-03 | P1 | DOM 采集与索引 | 先限制真正的遍历范围，再按时间预算处理队列 | 中：动态容器、Shadow DOM、虚拟列表 |
| PERF-04 | P2 | 抖音帧处理与共享悬停 | 依据 trace 减少重复布局读取与无变化写入 | 高：运动、坐标、全屏及原生恢复 |
| PERF-05 | P2 | 生命周期和后台唤醒 | 建立资源账本，优化证实无必要的维护工作 | 中：SPA 探测和恢复时机 |
| PERF-06 | P2 | 失败诊断与存储 | 降低同步采集及整包校验/写入成本 | 中：现场准确性、MV3 重启、导出清空顺序 |
| PERF-07 | P3 | 雷达 UI/流量统计 | 在测得热点后减少无变化更新和重复遍历 | 低至中：倒计时和自动阈值 |
| PERF-08 | P3 | 构建和设置页 | 量化加载成本后再裁剪依赖或延迟初始化 | 中：多入口注入顺序与资源定位 |

### PERF-01：雷达窗口与分组增量维护

**证据：** [runtime.ts](../src/features/repeat-reminder/runtime.ts) 对每次有效输入依次调用 `detector.ingest()` 和 `triggeredSuggestion()`。前者执行 `prune()`，后者经 `groups()` 再次清理并遍历整个 `entries` 重建 Map/Set。若窗口含 N 条记录、输入速率为 R，相关遍历成本随 R × N 增长；这是复杂度分析，尚非实测耗时。

**方案：** 先新增纯逻辑基准和输出对照，再用按文本维护的计数、发送者引用计数、最新文本记录与到期索引替代全量重建。精确计数和相似簇选择分开维护；仅刷新受本次输入/过期影响的分组。到期清理要覆盖 ID、指纹和簇索引，而非只清理 `entries`。

**边界：** 简单 FIFO 到期要求时间有序，必须先确认 `observedAt` 的乱序行为；否则采用能处理乱序的到期结构。删除文本、切房、阈值变化、代表文本切换均要同步撤销索引。不能静默加采样或截断精确计数来限制内存；若峰值仍需降级，应另行明确产品行为。

**验收：** 同一确定性消息序列上逐步比较现实现与优化实现的建议输出；覆盖 60 秒边界、3 秒镜像、10 分钟 ID/簇过期、未知发送者、忘记文本、手动/自动阈值以及切房。再比较高流量下耗时和分配量。

### PERF-02：相似度特征和评分复用

**证据：** `resolveCluster()` 已按 bigram 索引找候选，不能当作毫无索引的全量比较。但它对候选先调用 `areRepeatReminderTextsSimilar()`，通过后再调用 `repeatReminderSimilarity()`；后者重建 profile、集合并计算编辑相似度。共享前缀多时，候选集合仍可能较大。

**方案：** 优先让一次候选评估返回可复用的分数与资格结果；按规范化文本缓存 profile/字符集合，随簇或窗口生命周期清理并设容量限制。先记录每次候选数、实际评分次数、缓存命中率，再决定是否调整索引。

**边界与验收：** 保留数字、URL、拉丁 token、否定词和 Emoji 保护规则及短文本阈值。不靠粗暴截断候选数量改变匹配结果。测试同时保留“相同前缀的数字变体”等压力输入；此前自动阈值测试改用无关单字是隔离测试职责，不等于解决了相似度成本。

### PERF-03：让 DOM 扫描和队列工作真正有界

**证据：** `collector.ts` 的 `discoverRoots()` 使用 `Array.from(querySelectorAll('*')).slice(0, 4_000)`，`scanRoot()` 在取得全部匹配后才取末尾 240 个。这限制了后续处理数量，没有限制 selector 查询和数组物化成本。带 `rootSelectors` 的路径不使用同一全页 Shadow Root 发现逻辑，应分别测量。`flush()` 每次先复制整个队列再取 200 项；sender index 删除子树也会遍历全部后代。

**方案：** 优先复用已知聊天/播放器根节点；合并包含关系重复的 mutation 子树；队列使用可提前停止的迭代。对于证实昂贵的通配遍历，考虑有节点/时间预算的 TreeWalker 或增量发现；不能把所有 selector 查询一律换成 JS 遍历。批次同时使用数量上限和执行时间预算，续批保持顺序。

**边界与验收：** 不能长期缓存失效容器；保留必要的根节点重发现，覆盖全屏和节点替换。任何削减 `forgetNode()` 清理的改动必须证明节点重新挂载不会读到旧签名。统计吞吐、队列等待及丢弃量，确保“更快”不是少处理了消息。`collector.spec.ts` 的局部根节点约束继续通过。

### PERF-04：抖音帧工作与悬停布局

**证据：** `page-app.ts` 每个活动实例的 `advanceModelFrame()` 读取 Canvas rect，再调度轨道及渲染；空轨道会停止继续排下一帧。DOM Renderer 已分读写阶段。通用胶囊定位会读取锚点和操作栏尺寸。这些调用本身不证明发生强制同步布局，需要 trace 确认读前是否存在使布局失效的写入。

**方案：** 优先定位同一帧内重复测量和无变化 style 更新。只有证实多实例之间读写交错导致布局抖动时，才考虑在现有调度边界集中读取并提交；保持纯轨道模型独立。尺寸缓存需由滚动、缩放、字体加载、容器变化和全屏事件失效，不能永久缓存 rect。

**验收：** 满载与空闲均测；原生全屏、网页全屏、缩放、连续图片表情、hover 冻结和恢复均不变。节点数有界，异常仍恢复官方 Canvas。公共 hover 修改覆盖 B 站、斗鱼、虎牙，不能只测抖音。

### PERF-05：生命周期、内存和隐藏页面

**证据：** 雷达有 1 秒路由检查，配置局部根节点时另有 1 秒根发现；抖音 MAIN world 有默认 500ms 维护周期，隐藏时暂停实例但维护调度仍需分析。这些任务有恢复用途，不应直接全部删除。

**方案：** 在测试/诊断模式统计创建与销毁的 Observer、监听器、Timer、RAF、Renderer 和缓存条目；复用现有 runtime 的 dispose 边界。仅在确认恢复不依赖高频维护后，降低隐藏时非必要任务频率或合并同一生命周期内的重复探测。

**验收：** 20 次切房后旧房间资源归零或回到明确的共享基线；隐藏/恢复、DOM 晚挂载、重复初始化和页面退出均正确。heap 中的保留引用要追溯到所有者；WeakMap 的存在不能单独证明无泄漏。

### PERF-06：失败诊断的成本与写入放大

**证据：** 当前失败 DOM 快照同步采集后再规范化，后台追加日志时会读取并规范化已有日志，随后整包写回。接近容量上限或多个标签页同时失败时，即使次数有界，也可能发生序列化和 I/O 放大。捕获路径内部对一个元素的直接文本子节点计数亦需单独检查，输出节点上限不自动等于全部遍历的时间上限。

**方案：** 分段测量捕获、脱敏、传输、后台队列和写入。优先减少不必要的中间数组及重复编码，给实际遍历工作计数并保留截断标记；保持跨信任边界的重新校验。若考虑后台合批，只合并当前串行队列中已经到达的写入，所有追加响应都应在持久化后完成，并保持清空/导出顺序。

**边界：** 不使用仅靠 Service Worker 定时器最终落盘的常驻内存缓冲；不把诊断存储转移到 `storage.sync`。不为节省时间省略脱敏、恢复原始 HTML/请求正文或增加凭据采集。若将快照延后采集，页面可能已变化，必须标明实际采集时间，不能仍声称是失败瞬间现场；因此先优化同步局部采集。

**验收：** 成功路径不采集，超过快照频率仍保留失败摘要；模拟存储失败、后台重启、重复消息、并发导出/清空、容量淘汰、旧 schema 数据及大 DOM。记录写入次数和队列 P95，校验附件可用性不退化。

### PERF-07：雷达 UI 与自动流量统计

**证据：** `ui.ts` 的倒计时使用 250ms interval，并有提示位置测量与动画；`traffic-flow.ts` 的 `snapshot()` 会清理并多次遍历样本。先统计实际调用频率和可见队列长度，不能仅由 interval 的存在判定为热点。

**方案：** 显示值未变化时避免写 DOM；没有可见提示时核实倒计时能停用；批量读取旧位置后再写入动画。只有流量快照确实占据明显成本时，再增量维护发送者/突发窗口统计，避免与 PERF-01 一次性混改。

**验收：** 到期、静默期、提示队列顺序、首次说明、自动阈值预热/迟滞和自动 `+1` 的受保护语义保持一致。

### PERF-08：入口加载和设置页

先记录 `build/extension` 各入口大小、平台实际加载脚本及重复注入情况，再评估资源延迟初始化和可消除的重复代码。设置页优化以打开耗时、重复渲染和大量收藏场景为依据；不为少量静态控件引入新框架或虚拟列表。

涉及入口/构建前阅读 [入口运行时架构](ENTRY_RUNTIME_ARCHITECTURE.md) 和 [拆分检查清单](ENTRY_REFACTOR_CHECKLIST.md)。不得以减包为由合并 MAIN/isolated world，改变 manifest 注入顺序或移除必要 iframe 能力。

## 5. 实施与回归流程

每项单独形成可审查的改动：**保存基线 → 加行为对照或有针对性的压力用例 → 最小实现 → 同负载复测 → 核对功能与资源回收 → 记录收益/限制**。无稳定收益或出现语义变化时停止合入该项，不靠拉长 timeout 或降低压力取得通过。

阶段建议：

1. P0：完成基线和负载生成，建立内存/生命周期观测。此阶段不承诺收益。
2. P1：先 PERF-01，再 PERF-02；PERF-03 根据 trace 和 DOM 压力场景结果推进。
3. P2：独立处理渲染、生命周期、日志问题，逐项复测；不得把所有改动合成无法归因的一次比较。
4. P3：只有加载或 UI 的测量结果支持时实施；无需为了完成清单而重写已足够快的模块。

### 5.1 现有可运行命令

从仓库根目录运行。以下保留通用验证命令；本轮实际执行结果及新增基准命令见 [性能优化结果](PERFORMANCE_RESULTS.md)。

```bash
# 雷达算法/采集改动的针对性验证
npm run test:unit -- src/features/repeat-reminder/__tests__

# 较大功能或跨平台改动的完整门禁（包括构建和契约回归）
npm run check

# 只执行浏览器验证时，先以当前源码构建
npm run build

# B 站既有悬停压力场景
npm run test:browser -- --browser=chrome --scenario=bilibili-hover-performance
npm run test:browser -- --browser=edge --scenario=bilibili-hover-performance
```

若同一工作流刚完成 `npm run check` 且源码未变，复用其构建，不再重复 `npm run build`。浏览器可执行文件通过 `DANMAKU_E2E_CHROME_PATH` / `DANMAKU_E2E_EDGE_PATH` 配置，填本机实际路径；默认候选以 Windows 安装路径为主。

| 改动 | 现有场景选择 | 需要另外补充的验证 |
| --- | --- | --- |
| 公共采集、悬停和雷达 | `bilibili-hover-performance`；四平台各自的 `*-side`、`*-fullscreen` 实际场景 | 确定性流量压力、动态根替换、乱序和窗口对照 |
| 抖音渲染 | `douyin-side`、`douyin-fullscreen`、`douyin-auto-scale` | `www.douyin.com` SPA、长时间 Worker 生命周期及 Canvas 恢复的真实页面验收 |
| 发送诊断/日志 | `bilibili-precise-logs`；相关平台发送和富表情场景 | 多标签页失败风暴、存储异常、重启、容量及队列指标 |
| 设置 UI/收藏渲染 | `settings-zh`、`settings-en`；相关侧聊收藏场景 | 大收藏集、键盘焦点与鼠标操作、设置同步语义 |

表中的 `*-side` / `*-fullscreen` 只是场景类别，命令需填写 [运行器](../tests/browser/run-browser-e2e.cjs) 中单个完整名称。`--scenario` 不支持通配符、逗号列表；省略场景会跑所选浏览器全套，省略浏览器则要求 Chrome 与 Edge 均可用。大范围运行时优先一次执行完整套件。

每次运行后查看 `test-results/browser-e2e/summary.json` 及对应 JSON、截图、stdout/stderr，保留 attempt 和首次失败原因。可使用 `--artifact-root=独立目录` 隔离各轮产物；默认目录中的筛选执行会覆盖 summary，同名场景产物也会重建。运行器逐场景保存已完成结果，进程中断时仍须核对是否跑完所有请求场景。不得将旧产物、历史通过或重试后的单次通过当作全部证据。浏览器 E2E 保持本地可选，不加入 CI；30 分钟 `lifecycle-soak` 和 `*-startup` 只在明确选择时执行。
